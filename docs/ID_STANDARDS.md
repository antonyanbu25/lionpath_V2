# ID Standards — Centralized Entity ID Generation

All first-class domain entities use a **prefixed UUID v4** generated by a single module. See [ENTITY_CATALOG.md](./ENTITY_CATALOG.md) for which objects get IDs.

---

## Format

```
{prefix}_{uuid-v4}
```

Example: `usr_a1b2c3d4-e5f6-7890-abcd-ef1234567890`

| Entity type | Prefix | `newId()` argument |
|-------------|--------|-------------------|
| User | `usr_` | `"user"` |
| Team | `team_` | `"team"` |
| Account | `acc_` | `"account"` |
| Contact | `con_` | `"contact"` |
| Lifecycle | `lc_` | `"lifecycle"` |
| PrepBrief | `prep_` | `"prep"` |
| PostCall | `call_` | `"postCall"` |
| Task | `task_` | `"task"` |
| LifecycleEvent | `evt_` | `"event"` |

Prefixes aid debugging and log scanning. They are **not** a substitute for type checking — always store entities in the correct collection.

## Modules

| Runtime | Path | API |
|---------|------|-----|
| Browser | [`web/domain/id.js`](../web/domain/id.js) | `newId(type)`, `ID_PREFIXES` |
| Worker | [`worker/src/domain-model/id.ts`](../worker/src/domain-model/id.ts) | `newId(type)`, `EntityIdType` |

[`web/domain/types.js`](../web/domain/types.js) re-exports `newId` from `id.js` for backward compatibility.

## Usage rules

### Do call `newId(type)` when:

- Creating a User, Team, Account, Contact, Lifecycle, PrepBrief, PostCall, Task, or LifecycleEvent
- At entity creation boundaries in:
  - [`account-service.js`](../web/domain/account-service.js)
  - [`lifecycle-service.js`](../web/domain/lifecycle-service.js)
  - [`dual-write.js`](../web/domain/dual-write.js)
  - [`seed-dev.js`](../web/domain/seed-dev.js)
  - Migration scripts

### Do not call `newId()` when:

- Adding nested JSON inside `prep`, `analysis`, or event `payload`
- Creating enum values (`role`, `stage`, `status`)
- Generating OAuth state tokens or other non-domain identifiers (use `crypto.randomUUID()` directly)

### Do not use as IDs:

- Email addresses
- Company names or slugs (slugs are **lookup keys**, not FKs)
- Firebase `authUid` as `ownerId` (use internal `User.id`; see [adr/001-user-identity.md](./adr/001-user-identity.md))

## Stable dummy IDs (dev only)

For dummy auth mode, demo users use **deterministic** internal IDs so localStorage data survives re-seeds:

```javascript
stableUserIdForEmail("se@freshworks.com")  // usr_dummy_se_freshworks_com
```

Implemented in `id.js` — distinct from random `newId("user")` used for production user creation.

---

## Migration from legacy IDs

| Legacy | Target |
|--------|--------|
| `dummy-{email}` as User.id | `usr_dummy_{normalized_email}` via `stableUserIdForEmail` |
| Firebase uid as User.id / ownerId | Internal `usr_*` + `authIndex/{firebaseUid}` |
| Raw `crypto.randomUUID()` on tasks/history | `newId("task")`, `newId("postCall")` |

Run [`worker/scripts/migrate-user-ids.mjs`](../worker/scripts/migrate-user-ids.mjs) for Firestore cutover.
